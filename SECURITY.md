# Security notes

FieldOps is a portfolio backend, but its authentication path is designed around real security boundaries rather than demo-only plaintext credentials.

## Implemented controls

- Passwords are never stored directly. They are salted and derived with `hashlib.scrypt` using per-user random salts.
- Login returns short-lived HS256 JWT access tokens. The signing secret comes from `JWT_SECRET` and is generated by the Render Blueprint for hosted deployments.
- Authorization is checked against the current user record in the database on every protected request. A stale role claim inside an already-issued token therefore does not grant stale privileges after a role change.
- Public self-registration always creates a `viewer`; clients cannot self-select an elevated role.
- Admin privileges are bootstrapped only when both `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD` are explicitly configured.
- Work-order mutations are role-gated and creation records the authenticated creator.
- Production credentials are excluded from version control. `.env` is ignored and `render.yaml` prompts for bootstrap credentials.

## Role model

| Role | Read work orders | Create/update | Delete | Manage users/roles |
| --- | --- | --- | --- | --- |
| viewer | yes | no | no | no |
| technician | yes | yes | no | no |
| manager | yes | yes | yes | no |
| admin | yes | yes | yes | yes |

## Known limitations

This project does not yet implement refresh tokens, token revocation lists, MFA, rate limiting, email verification, password reset, audit-event persistence, or distributed secret rotation. Those would be required before using the service for sensitive production workloads.

Do not reuse development or CI credentials in a real deployment.
